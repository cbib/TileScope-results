# Scenario benchmark

This package builds deterministic expression and topology archetypes on real
spatial-transcriptomics substrates. The generator is independent of TileScope: it does not
import TileScope internals.

## Active scenarios

| Scenario | Defining pattern | Roles |
|---|---|---|
| `broad_colocalization` | broad A and B in one ROI | positive + independent-B null |
| `focal_pattern` | focal A and B in one ROI | colocated/separated modes + independent-B baseline |
| `spatial_gradient` | concordant/opposed ramps in one ROI | positive + B-overlay permutation |
| `nested_foci` | broad A with focal B activity inside A | positive + matched B-focus relocation |
| `embedded_domains` | one to three B-labelled domains inside A | positive only |
| `dispersed_infiltration` | many dispersed B-labelled components inside A | positive only |
| `contact_interface` | boundary-conditioned activity between adjacent ROIs | two modes with matched ablations |

`territorial_exclusion` is not an active standalone scenario. Broad adjacent
compartments without boundary conditioning are already represented by the
contact-interface ablations.

Scenario definitions, comparison roles and generator invariants are in
[CONTRACT.md](CONTRACT.md).

## Architecture

- `SampleScaffold` is the sole sample geometry authority.
- `PairInterface` supplies pair geometry where a scenario needs it.
- `enclosure.py` classifies observed B components once per builder call.
- `spatial_primitives.py` owns reusable connected-patch operations.
- `SampleBackgroundBank` supplies deterministic background fields shared by
  the roles of one case.
- Scenario modules own their live role contracts. `registry.py` owns only the
  geometry-source and morphology metadata.
- `materialize.py` caches each scaffold and source hash once per sample.

The plan declares cases and parameters, not a duplicate role contract. Each
generated manifest records the role contract resolved from the scenario
module.

## Inputs and outputs

Input Data contains both the published corpus and the geometry needed to
regenerate its 30 cases (57 role datasets). No original expression matrices
or Seurat objects are needed for this regeneration.

```
TileScope-data/input_data/benchmark/
  source_samples.csv                  # dataset/sample -> source CSV
  source_geometry/                    # four geometry-only CSVs
  tilescope_run_config.json            # for analysing the generated datasets
  corpus/
    benchmark_plan.json
    corpus_index.json
    <scenario>/<case_id>/
      manifest.json
      truth_ledger.csv
      <role>.csv
```

`source_samples.csv` lists 13 source samples. Paths are relative to that
inventory: nine reuse the human or mouse score banks in Input Data; four
point to `source_geometry/`. Only coordinates (`x`, `y`) and ROI labels
(`roi_id`) are read. Expression values are generated by the scenario code.
Keep the complete Input Data directory together, not just `benchmark/`.

Running `materialize.py` with its default settings writes to a separate
writable sibling so the bundle is never modified:

```
TileScope-data/scenario_benchmark/
  corpus/                              # generator output; separate from the bundle
    corpus_index.json
    feasibility_availability.csv
    feasibility/                       # optional wider feasibility audit
    <scenario>/<case_id>/
      manifest.json
      truth_ledger.csv
      <role>.csv
  CurrentResults/
    tilescope_run_config.json
    <scenario>/<case_id>/<role>/       # full core outputs
```

Extracted statistics and run accounting are written to
`TileScope-results/analyses/scenario_discriminability/outputs/`.

Generated observations are reproduced from the bundled case plan, source
geometry and scenario code. Each new index records the output hashes and
generator provenance. Keep the exact run config with its TileScope result
batch, including when archiving CurrentResults.

The location is controlled by `TILESCOPE_DATA_DIR` (the entire data root).
The default is a sibling `TileScope-data` directory. Feasibility tables remain
with the corpus; derived analysis tables use the results location above.
See [the storage contract](../docs/DATA_LAYOUT.md). References beginning with
`corpus/` in saved manifests are logical names resolved to this external tree.

## Commands

```bash
# Regenerate the corpus from the bundled plan into the writable sibling
# TileScope-data/scenario_benchmark/corpus/ (defaults; overridable with
# --plan, --sources, --output).
python -m scenario_benchmark.materialize --dry-run
python -m scenario_benchmark.materialize
python -m pytest tests/scenario_benchmark
```

The generator reads `benchmark/corpus/benchmark_plan.json` and
`benchmark/source_samples.csv` from Input Data. `--output DIR` selects the
destination for new case directories and their `corpus_index.json`;
`--index FILE` optionally changes the index destination. The published index
is not an input to regeneration and is not overwritten. Outputs inside the
downloaded Input Data directory are rejected. Use `--verify-determinism`
only for audits or CI; ordinary materialization does not generate every
case twice.

`--audit` is a separate, wider search for eligible geometries across the
original sample collections registered in `datasets.py`. It requires those
collections, beyond the 13 samples supplied for the published benchmark.
It is not required to regenerate the published corpus.
